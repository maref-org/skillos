## 三、P0 阻塞项（必须修复方可发布）

### P0-1 · Audit Logger 实现完整但业务代码零调用

| 项 | 内容 |
|---|---|
| 手册条款 | §2.3 Code Review 必审 8 项之"敏感操作有审计日志"；§5.1.2 Multi-Agent 可解释性"异常行为有审计日志" |
| 证据 | `skillos/audit.py:68` 定义 `AuditLogger` 类（HMAC-SHA256 + 链式哈希 + 16 类事件 + 脱敏），`db/models.py:125` 有 `AuditLogModel`，但 `grep -r "AuditLogger\|from skillos.audit" skillos/` **仅命中 `audit.py:72` 的 docstring 示例**，业务路径（Skill 执行、Settlement、Auth）零调用 |
| 影响 | 高风险操作（skill 执行、结算提交、配置变更、认证失败）运行时不产生审计日志，事故无法追溯 |
| 修复建议 | 在 `EntryKernel.human_gate()`、`SkillKernel.execute()`、`DistributionEngine.distribute()`、`IdentityClient.verify_signature()` 等关键路径调用 `AuditLogger.log()` |

### P0-2 · Prompt 注入防御完全缺失

| 项 | 内容 |
|---|---|
| 手册条款 | §4.3.1 安全扫描流水线 Prompt 注入防护；§5.1.1 LLM 应用验收"无法通过注入绕过安全策略"；§1.2 GA 级要求"Prompt 注入防护" |
| 证据 | `grep -ri "prompt_inject\|injection\|sanitize_prompt\|safety_check\|hallucin" skillos/` **零匹配**。`skill_kernel.py:239` 的 `forbidden_keywords` 仅过滤 `os.system/subprocess/eval/exec/__import__`，是 payload 关键词过滤，不是 LLM prompt 注入防御 |
| 影响 | 用户输入若直接进入 LLM 上下文（虽 `EntryKernel._classify_intent` 当前是关键词匹配，但 `litellm` 是 optional-dep，一旦接入即暴露）可绕过安全策略 |
| 修复建议 | 在 LLM 调用前增加 prompt 消毒层（system prompt 隔离、用户输入 fence、 jailbreak 检测分类器）；至少在 `EntryKernel` 接入 LLM 前完成 |
| Beta 例外评估 | 不允许例外（HITL 兜底不足以替代注入防御） |

### P0-3 · Agent 间通信明文 HTTP，无 TLS/签名

| 项 | 内容 |
|---|---|
| 手册条款 | §5.1.2 Multi-Agent 通信安全"Agent 间通信加密"；§3.2 L1 后端"CORS/安全头" |
| 证据 | `protocol_gateway.py:127` A2A/MCP 路由硬编码 `http://localhost:8000/mcp/v1/{target_id}`；仅传播 `X-Trace-ID`/`X-Span-ID` 头，**无 TLS、无 HMAC、无消息签名**。加密能力存在于 `negmarket/storage.py:23` (AES-GCM) 和 `protocol/identity_client.py:161` (Ed25519) 但**未用于 Agent 间通信** |
| 影响 | 跨 Agent 调用可被中间人篡改/重放，拜占庭共识机制失效 |
| 修复建议 | 强制 HTTPS（已有 `--insecure` flag 机制，需设默认拒绝 HTTP）；为 A2A 消息增加 Ed25519 签名头 |

### P0-4 · SLO 已定义但运行时零采集

| 项 | 内容 |
|---|---|
| 手册条款 | §2.5.1 PRR"可观测性覆盖四大黄金信号"、"SLO/SLI 已定义且业务方认可"、"错误预算已计算并接入燃烧率告警"；§4.5.1 应用层"QPS/延迟/错误率" |
| 证据 | `skillos/kernel/slo.py:81-102` 定义 4 个 SLO（skill_call/protocol_gateway/negmarket_api/kernel_routing），`slo.py:108,115` 定义 `record_latency`/`record_availability`，但 `grep` 全树业务代码零调用。`metrics.py:63-83` 的 RED Counter/Histogram 也需手动调用 `record_request()`，**未见 FastAPI/Starlette 中间件自动埋点** |
| 影响 | 发布后无法验证 P99/可用性/错误率是否达标，错误预算燃烧率告警无法触发 |
| 修复建议 | 增加 ASGI 中间件自动埋点 RED 指标 + 调用 `SLOManager.record_latency()`；或在 `EntryKernel.route()` / `ProtocolGateway.dispatch()` 入口埋点 |

### P0-5 · pre-push hook 未通过工具链自动安装

| 项 | 内容 |
|---|---|
| 手册条款 | 治理框架红线第 2 条"禁止绕过 pre-push hook（`--no-verify`）"；AGENTS.md 治理合规检查清单第 3 项"pre-push hook 已就位" |
| 证据 | `.pre-commit-config.yaml` 存在但 `athena-leak-check` 仅配置 `stages: [pre-commit]`；`scripts/sanitize-for-push.sh` 是手动脚本；无 `.husky/`、无 `core.hooksPath` 配置、无 hook 安装脚本 |
| 影响 | 治理红线被绕过风险；宪法第 4-A 条第 2 项不满足 |
| 修复建议 | 执行 `pre-commit install --hook-type pre-push` 或在 `scripts/sanitize-for-push.sh` 安装到 `.git/hooks/pre-push` |
